# Marketing performance observations

Prepared 11 October 2026 in release 2.53. **Not deployed.** Production remains 2.52.0. This is an owner-only record of observed public post aggregates, not a direct provider connection, an independent audit, automatic optimisation or an acquisition result.

## Why it exists

The 11 October marketing review found platform results in operator notes while the cloud planner could only see website campaign events. The new Marketing desk section, “What happened after posting?”, retains platform observations and lets the next eligible new planner context use them without inventing attribution. See [the real baseline and two-week experiment](MARKETING_REVIEW-2026-10-11.md).

## Daily operating procedure after deployment

1. Reconcile due provider schedules and exact public delivery first, following SOCIAL_PUBLISHING.md. A performance observation never changes a brief, review, schedule or delivery receipt.
2. Inspect the existing observation history before collecting another observation. Use the connected Metricool brand 7294726 for Facebook Page 1319703417896763 and Instagram sponsorintellondon; use native LinkedIn for company 146710167 and the approved personal profile. Check the exact author and public post URL at the provider. The form's account checkbox is an operator attestation, not automatic account verification.
3. Record the actual inspection time, the reporting window shown by the platform and its timezone. Date fields use the browser's local timezone and are saved in UTC; the separate timezone describes the provider's reporting convention. Leave the exact publication time blank unless established. Do not turn a relative “days ago” label into an invented exact timestamp. A lifetime view has no invented start date; a period view needs its actual start and end. If a provider's time boundary cannot be established, do not fabricate it to satisfy the form.
4. Copy only displayed, supported post metrics. Zero requires an explicit zero. A missing post row, unsynchronised analytics or a provider failure is unknown; use unavailable with all metrics blank when an exact post and reporting window are known. General clicks and external link clicks are different fields. Notes explain incomplete coverage, definitions and uncertainty. No audience profiles, names, messages, CVs, tokens or customer details belong here.
5. Historical native posts may be recorded without an editorial brief. They remain separate from tracked campaigns. Copy a campaign URL only when that exact recognised link appears in the post and belongs to the selected account. Never add tracking retrospectively or convert general clicks into website events. The private performance record does not claim that an untracked post caused a website action.
6. Select **Agent-assisted through owner account** for agent work. Save once and inspect the retained reference. An uncertain save must be reconciled against history or retried with the identical request; it must not become a new observation. Corrections reference the preceding observation of the exact same account/post, explain why and append a new version. The original stays visible. Concurrent corrections cannot both win.
7. Prefer approximately 24-hour and seven-day reads where a real publication time is known. Compare compatible ages, windows and definitions before proposing one weekly change. With sparse or missing evidence, retain the uncertainty and choose no change where justified. Follow the current two-week experiment; no observation raises spending, posting cadence or model allowances.

## Storage and planner contract

The owner-only GET/POST route is `/api/admin/marketing/performance`. Existing owner authentication and same-origin mutation checks apply. POST is bounded to 8 KB and 20 attempts per owner per hour, using the existing rate limiter; it does not call a provider or model. The account/provider allowlist, native permalink, clean analytics URL, dates, reporting timezone, finite integer metrics and recognised campaign/account relationship are validated. Actor identity comes from the authenticated server session. Titles/notes are escaped in the UI; all planner evidence remains untrusted data.

Migration 0035 adds one append-only table, two indexes and two triggers. Request hashes provide idempotence; a unique first-observation identity rejects the same exact post/time/window under a new request key. A correction has one unique predecessor, and insertion plus audit are atomic. Updates and deletes are rejected. The UI exposes the latest 100 observations including corrected history. Native LinkedIn share/activity aliases are not automatically proven equivalent: retain the originally verified permalink consistently and inspect history before saving.

A new immutable planner context includes at most 20 observations from the latest 100 uncorrected rows observed in the last seven days, with reporting end also inside that period. Only the latest cumulative observation per account/post/window type/timezone is selected; distinct period windows remain distinct and must not be summed. Private operator notes, evidence URLs, actor identity, request keys and hashes are excluded from model context. Public title, post link, dates, metrics, optional recognised campaign ID and agent/owner observation label remain. Existing captured contexts are not rewritten when later observations or corrections arrive.

Policy `sourced-guides-and-observed-performance-v4` explicitly prohibits treating unknowns as zero, summing overlapping reach, inferring unique people or causal conversion, declaring a sparse-data winner, or using metrics to clear a hold. Topic eligibility, source checks, independent review, account allowlists, queue slots, company cadence and shared AI allowance remain unchanged. No extra model call is introduced. This is evidence available to a bounded planner, not training model weights or proof that its decisions improve growth.
