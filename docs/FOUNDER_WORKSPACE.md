## Explicit saving and recovery

The signed-in Founder hub can explicitly open one private workbook per account. The workbook contains the existing 15 text prompts, self-marked stage checklist, curated provider shortlist and fee-location choice. It is separate from the career workspace, so an older career client cannot erase it. Opening does not send tab notes to the account. A user compares existing copies when needed, then explicitly chooses Save. There is no autosave to the server, model input, attachment upload or external application/contact.

Opening also opts into an account-scoped browser copy containing current notes, the last acknowledged base, revision, any pending exact request and one displaced recovery workbook. It is read back before a write request. Storage failure or a changed device copy leaves the current notes in memory with an explicit error. Copyable JSON is available when downloads are blocked. A download request does not prove file delivery. Browser/site-data removal can erase device copies; they are not remote backups.

A reload requires the app to load, signing in and opening the private workbook again. Offline recovery here means the workbook API is unavailable while the app still loads; an offline app shell is not implemented. Unsynced changes remain separate from the last saved base. A saved response belongs to the authenticated account; an unexpected identity never replaces the current copy. Session expiry hides account notes while retaining unsaved memory for that same owner in the current tab, including storage-failed edits. Other accounts cannot open that retained memory. Closing the tab can still lose memory-only work; the unload warning is a best-effort browser affordance, not a persistence guarantee.

A concurrent save returns a conflict. The interface shows both copies and requires an explicit choice. A displaced nonempty copy remains in device recovery. An existing recovery copy must be resolved before another replacement. Restoring it changes local notes only; saving and removing recovery remain separate decisions. Emptying current notes is also an explicit edit and cannot silently restore a newer cloud copy. Damaged device data stays available as raw text and cannot be overwritten by a cloud read or exposed under a changed identity.

## Server and account boundaries

`/api/career/founder-workspace` uses existing origin/session protections. Reads and writes are private/no-store and select the authenticated user. Submitted account ID is a stale-session check, never authority to select another user. Strict canonical workbook validation rejects unknown fields, invalid curated IDs, malformed/oversized data and executable-shaped input.

Each Save includes an expected revision and a UUID request key. A transaction writes the current workbook and its request receipt together. Concurrent distinct requests yield one successful revision and one conflict. Repeating identical content/revision with the same key returns its original acknowledgement even after later saves. Reusing the key for different content is rejected. Failed or lost responses keep the exact pending request; edits made meanwhile remain separate. Only a receipt-aware revision conflict clears that pending request without a successful acknowledgement. New save attempts are limited to 20 per account/hour; acknowledged exact replays do not create new revisions or consume another save allowance. Rate-limit bookkeeping is separate from the content transaction.

Migration 0047 adds `founder_workspaces` and `founder_save_receipts`. The former holds only the current workbook. Receipts hold request/content hashes, revision and time, not historical note text. This is not a full revision-history product. Both tables reference the account and cascade on existing authorised account deletion. The final save statement also checks user existence, so a request authenticated before deletion cannot recreate the workbook afterward. Actual local Worker/auth/D1 tests verify both orderings and receipt-write rollback.

Sign-out checks the device record and any open in-memory workbook before ending the session. Unsaved, uncertain or recovery work must first be saved/exported and explicitly resolved. Clean sign-out removes only the unchanged expected device copy; concurrent changes or cleanup failures remain explicit. Account deletion removes the cloud tables and attempts browser cleanup after server success, without claiming that failed cleanup succeeded. Exports and copies on other devices remain. Career backups do not include Founder workbooks: use the hub's separate JSON/readable export. No owner/customer account was deleted in validation.
