# Release 2.98.15 — preserve uncertain source dispatches

A lost workflow-create response followed by unavailable provider history previously changed a source run to `dispatch_failed`. The next new-ID request could bypass that row. An overlapping same-ID request could also call the creator again. Fictional counterexamples reproduce both paths; no production duplicate execution was established. The production inspection found 108 terminal source runs and no open/unconfirmed source row. This is not an explanation for the missing 2/3 November evening runs.

The dispatcher now admits one create attempt through its atomic new-row reservation. An existing ID is reused, including queued rows; a lost database acknowledgement cannot authorise a create. An uncertain provider response keeps the row queued with an explicit explanation, preserving its hold and allowing the original delayed workflow to initialise. Existing `dispatch_failed` rows also block new dispatches. Only the existing original-ID terminal-status reconciliation can release an old open run. Status unavailability, elapsed time and a new UTC day cannot do so. No request limit, source approval, advert hold, pause or catalogue check changes.

This intentionally favours preserving uncertainty: if execution stopped between reserving the row and calling the provider, the row remains held until its original outcome is separately resolved. The release does not add a replacement/recovery service or infer that missing provider history proves no execution. Cloudflare's [Workers API](https://developers.cloudflare.com/workflows/build/workers-api/) distinguishes instance statuses and rejects creation with an existing ID; the duplicate same-ID finding is a repeated create attempt, not proof of two provider instances.
